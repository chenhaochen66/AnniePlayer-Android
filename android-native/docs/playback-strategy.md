# 播放链路策略（设计稿）

> **状态**：设计决策记录。只写「应该怎样」，不写「现在怎样」。
> 实现与本文冲突时，先质疑实现，再质疑本文。
>
> **范围**：Kotlin 版（`android-native/`）。输出模式、位完美判定、设备变化、状态切换、特殊场景。
> **不含**：解码格式细节、下载链路、歌词、UI 视觉。

## 0. 一句话总纲

> 用户只选**意图**（模式、开关），通路由**探测**决定，状态由**实测**描述。

三件事必须分开，混在一起就是现在所有混乱的来源：

| 层 | 内容 | 谁决定 | 持久化 |
|---|---|---|---|
| 意图层 | 模式（3 档）、bit-perfect 开关 | 用户 | 是 |
| 通路层 | 实际在跑哪一档、哪个设备、什么参数 | 引擎探测 | 否 |
| 事实层 | 采样率 / 位深 / sharing mode / 时钟源 / 缓冲 | HAL 回读 | 否 |

## 1. 概念模型

### 1.1 三档输出模式

三档不是「三个音质等级」，而是**三种控制权归属**。

| | 系统默认（AudioTrack） | AAudio 独占 | USB 独占 |
|---|---|---|---|
| 谁控制采样率 | AudioFlinger | 我方 + HAL | 我方 + DAC |
| 谁控制混音 | AudioFlinger（必混） | 无 | 无 |
| 我方主动 SRC | **是**（见 §3.2） | 否（跟随源） | 否（跟随源） |
| 位完美可能 | **结构上不可能** | 可能 | 可能 |
| 时钟源 | AudioTrack playback head / AudioTimestamp | MMAP 硬件戳 → framesRead → written−buffer | DAC 反馈端点 |
| 音量语义 | 软件音量可用 | 锁 1.0（位完美时） | 锁 1.0 或硬件音量 |
| 延迟量级 | 40–100 ms+ | 10–30 ms | 取决于 DAC 缓冲 |

### 1.2 模式必须是两层

```
preferredMode   ← 用户选的，持久化，只有用户能改
      ↓ 由 reconcile 推导，受设备能力约束
activeRung      ← 当前真正在跑的，不持久化，设备变了就变
```

**规则：设备变化只改 `activeRung`，永不改 `preferredMode`。**

没有这一层会同时坏三件事：

1. 插蓝牙自动降级 → 表现为「静默篡改用户设置」
2. 断开蓝牙后不回归 → 用户要手动切回来
3. 设备抖动时反复重试失败组合 → 死循环

有了这一层，`failedRates` 这类黑名单只需要管「这个组合在这台设备上到底行不行」，不用管「用户想听什么」。

用户可见文案：

> 模式：AAudio 独占（当前：系统默认 · 蓝牙不支持独占）
>
> 模式：USB 独占（当前：系统默认 · 未检测到 USB DAC）

### 1.3 三层职责划分

先拆开「下沉」这个词——它是**两件性质完全不同的事**：

| | 内容 | 特征 | 结论 |
|---|---|---|---|
| **数据面** | 位深打包、SRC、DSP、写循环体 | per-sample / per-buffer，在实时线程上 | **本来就在 native** |
| **控制面** | 停喂 → 读位置 → 关流 → 开流 → 校验 → seek → 恢复 | 有分支、有状态、150 ms–3 s 的事件 | **不下沉** |

「播放中切换模式涉及的音频操作」全部属于控制面。

| 层 | 内容 | 放在哪 |
|---|---|---|
| 策略 / 决策（控制面） | `reconcile`、降级规则、黑名单、提示判定、文案 | **Kotlin**（纯函数，可 JVM 单测） |
| 音频 I/O（数据面） | open / write / clock / 位深打包 | **Native**（JNI 粗粒度，per-buffer） |
| DSP / SRC（数据面） | 滤波与重采样 | **Native** |

**判据不是「涉不涉及音频」，而是「在不在实时线程 / 调用频率多少」。**

| 特征 | 该在哪 |
|---|---|
| 在音频回调 / 实时线程上执行（不能阻塞、不能分配） | **Native** |
| 每样本或每帧运算 | **Native** |
| 需在实时线程与主线程间原子共享的内存 | **Native 原语**（薄，单一职责） |
| 有分支决定「下一步做什么」 | **Kotlin** |
| 需读系统状态（AudioManager / 焦点 / 路由 / 设备） | **Kotlin** |
| 需更新 UI / MediaSession / 持久化 | **Kotlin** |
| 失败要弹哪一级提示 | **Kotlin** |

切换流程的 11 步（§6.1）**没有一步在实时线程上执行**，全在主线程 / 控制线程。按判据，一步都不该下沉。

**native 里不许有状态机。** 只暴露无状态或「单流状态」的函数：`open(config)` / `write(buf)` / `getClock()` / `close()`。凡是「下一步该做什么」的判断，一律回 Kotlin。

例外两个：

- **临界区下沉**是允许的——如果某个操作必须与写线程原子（如「读已播出位置并保证流存活」），只把**这一处**做成薄的 native 函数，不要把整个编排拖进去。「临界区下沉」与「编排下沉」成本差一个数量级。
- **USB 独占的 UAC 驱动**是天然的 native 模块（见 §12 Phase 5b），必须隔离，不许污染 AAudio/Oboe 通路。

完整论证（JNI 频率量化、三条成本、越界下沉的反面形态、「等没故障再下沉」为何是错判据、三个可量化触发条件）见 **§13 附录 A**。

### 1.4 状态收敛模型

不要写「命令式切模式函数」，写声明式收敛：

```
Desired = (preferredMode, bitPerfect, targetRate, dspOn, deviceRoute, sourceParams, positionMs, playing)
Actual  = (activeRung, realRate, realDepth, sharingMode, clockSource, bufferFrames)

reconcile(Desired, Actual) → Action
```

`Action` 只有七种：

```
Noop | Open(rung) | Reopen(rung) | Seek(ms) | Pause | Play | Notify(level, code)
```

两条铁律：

1. **幂等**：`Desired` 与 `Actual` 都没变 → 一律 `Noop`。不许因为回调来了一次就重开流。
2. **一次一步**：一轮 `reconcile` 最多产生一个 `Reopen`，防死循环。

## 2. 位完美

### 2.1 六条判据

不写死这六条，「Bit Perfect」就是营销话术。**六条全中才算**。

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 流实际采样率 = 源采样率 | `getSampleRate()` 回读 |
| 2 | 输出位深容器 ≥ 源位深，样本值未改写 | 16→16 / 16→24 补零（合法）；24→16 否决 |
| 3 | 无 32-bit float 中转往返 | int 源 int 直通 |
| 4 | 无音量缩放 | 软件音量恒 1.0，无淡入淡出、无 RG 归一化 |
| 5 | 无我方 DSP | EQ / 限幅 / 混响全部 bypass |
| 6 | 通路不经混音 | exclusive / direct，不跑 AudioFlinger mixer（会 dither） |

**补零不算改写**（左对齐补零，样本值相同），所以 16-bit 源输出到 24/32 位容器仍是位完美；降位深不是。

### 2.2 徽章四态

徽章不许预支结论。未实测就说「待定」。

| 态 | 外观 | 触发 |
|---|---|---|
| **不可达** | 灭 + 原因 | 结构不可能（蓝牙、系统默认档、空间音频开启） |
| **待定** | 灰 + 「待实测」 | 未播放 / 刚切模式 / 刚换设备 |
| **已达成** | 亮 | 播放中六条回读全部通过 |
| **已偏离** | 灭 + 「已调音 / 已改率」 | 播放中但用户破坏了条件 |

这四态还解决一个老困惑：暂停时徽章亮着，用户插上蓝牙后必须**立刻**变「不可达」，而不是等下次播放才发现。

想主动验证 → 设置里放「检测当前输出能力」，用户显式点击才短暂 open 一次并立即关闭。显式动作不打扰别人，隐式预建才打扰（见 §6.2）。

### 2.3 各档可达性

| 判据 | 系统默认 | AAudio 独占 | USB 独占 |
|---|---|---|---|
| 实际率 = 源率 | 可能 | 回读 | 回读 |
| 位深不降 | 可能 | 回读 | 回读 |
| 无 float 往返 | 不可验 | 我方保证 | 我方保证 |
| 无音量缩放 | 不可验 | 我方保证 | 我方保证 |
| 无 DSP | 可验 | 可验 | 可验 |
| 不经混音 | **否** | 回读 sharingMode | 结构保证 |

结论：**徽章只在两档独占下有意义，且必须由回读驱动，不能由「用户选了独占」推导。** 选择 ≠ 事实。

## 3. 引擎适配

### 3.1 目标采样率统一

一个概念，三档各自解释：

| 档 | 目标率 |
|---|---|
| 系统默认 | `自选率 ?? 设备原生率`（我方 SRC 打到这里） |
| AAudio 独占 | `自选率 ?? 源率`（作为 open 请求参数） |
| USB 独占 | `自选率 ?? 源率`，且必须落在 `getSampleRates()` 报的列表内 |

UI 只有一个选项，三档行为自动对齐。

### 3.2 系统默认档的主动 SRC

原则：**宁可自己做一次高质量 SRC，也不让系统做一次低质量 SRC，更不要两个都做。**

```
1. 读当前路由设备的原生率
2. 源率 == 原生率 → 什么都不做，直送
3. 源率 != 原生率 → 我方 SRC 到原生率
```

第 2 条必须显式判断。**无条件 SRC 是错误实现**——44.1k 源在 44.1k 设备上白做一次劣化。

**AudioTrack 不会自动适配新设备的采样率。** 路由变化后 AudioFlinger 只把已有 track 重路由，采样率仍是建 track 时定下的，新设备原生率不同就会被系统 SRC。所以系统默认档在路由变化后**必须主动重建**，用新设备原生率重算 SRC 目标。

### 3.3 各设备真实参数

| 设备 | app 侧采样率 | 位深 | 经编码 | SRC 目标 |
|---|---|---|---|---|
| 外放 | 设备原生（多为 48k） | 16/24 | 否 | 原生率 |
| 3.5mm 耳机 | 设备原生（多为 48k） | 16/24 | 否 | 原生率 |
| 蓝牙 A2DP | **44.1k 常见，不是 48k** | 16 | **是**（SBC/AAC/LDAC） | BT 实际率 |
| 蓝牙 LE Audio | 48k | 24 | 是（LC3） | 48k |
| USB DAC | `getSampleRates()` 列表 | 16/24/32 | 否 | 源率或 DAC 原生 |
| HDMI / DP | 48k 常见 | 16 | 否 | 原生率 |

**蓝牙那个坑必须记住**：`PROPERTY_OUTPUT_SAMPLE_RATE` 报的是主输出（外放）的率，不是蓝牙的率。A2DP 大概率 44.1k，若按 48k 做 SRC，编码器再重采样到 44.1 = 双重 SRC。正确做法：用 `AudioDeviceInfo.getSampleRates()` 查当前**路由设备**，取不到优先 44.1。

两个结论：

1. **蓝牙永远不可能位完美**，不管开关怎么开。结构性限制，不是能力问题。
2. **USB DAC 下 AAudio 独占已接近位完美**（系统直接把 PCM 交给 DAC）。真 UAC 独占边际收益很小（见 §12 Phase 5）。

### 3.4 内部转换 ≠ 用户可调项

开关只管用户可调项，不管引擎适配。这条边界要划清，否则「锁着还能变率？」会变成一个说不清的问题。

| 属于 | 受开关控制 |
|---|---|
| 避开双重 SRC 的那次自适应 SRC | 否（引擎行为） |
| 路由变化后的目标率重算 | 否（引擎行为） |
| EQ 开关 | 是 |
| 自选采样率 | 是 |
| 软件音量（待定，见 §10） | 待定 |

### 3.5 独占通路下的 DSP 与自选采样率

**结论：AAudio 独占 + 调音 + 自选采样率是一个成立且推荐的组合。**

独占约束的是「有没有混音器介入」，不是「数据里是什么」。AAudio 拿到的是我方填进去的 PCM 字节流，写之前做 SRC、做 EQ 它不知道也不关心。

#### 3.5.1 正确数据流

```
解码（PCM）
  ↓
[float 域] SRC → 目标率
  ↓
[float 域] DSP / EQ（系数按目标率计算）
  ↓
打包成 I16 / I24_PACKED / I32
  ↓
AAudio write()    ← 独占流，全程不经混音
```

关键：**float 域只出现一次，打包只做一次。** 劣化的来源不是「做了处理」，而是「int↔float 来回转换多次」。

#### 3.5.2 采样率：先 open 回读，再定 SRC 目标

「自选采样率」有两个不同含义，混淆会产生变调：

| 含义 | 做法 |
|---|---|
| **(a) 请求率** | `setSampleRate(96000)` 告诉 HAL 你要什么 |
| **(b) 我方 SRC 到目标率** | 把数据重采样到某个率再喂 |

**正确顺序**：

```
1. 用「用户选的率」open
2. 回读 getSampleRate() → realRate
3. realRate 才是 SRC 的目标
4. 按 realRate 喂数据
```

**绝不能反着做。** 先 SRC 到 96k，而 HAL 只给了 48k → 96k 的数据被当 48k 播 → **速度翻倍、音调升一个八度**。这是「自选采样率」最典型的翻车方式。

好消息：**流不会骗你，它会明确告诉你它跑什么率，迁就它就行，不需要重开流。** 回读不符时改 SRC 目标，比关流重开便宜得多。

位深同理：请求 `I24_PACKED`，HAL 只给 `I16` → 按实际格式打包（有损但不崩）。一律「优先迁就，不重开」。

#### 3.5.3 三个实现细节

**① 改采样率 → EQ 系数必须重算**

Biquad 系数是采样率的函数。44.1k 算好的系数拿到 96k 用，频响整体偏移（例：100 Hz 低切跑到 217 Hz）。这是**静默错误**——不崩、不报错，只是听起来怪。

同理，EQ 放在 SRC 之前（源率域）系数按源率算，放在之后（目标率域）按目标率算。**两种都对，但必须始终一致**，不许一处按源率、一处按目标率。

**② 重活不要放在写临界路径里**

写线程是阻塞写（20 ms 超时）。SRC + EQ 单次耗时超过缓冲时间就 underrun，100 ms 缓冲也救不了。

```
生产侧（解码线程）：解码 → SRC → DSP → 打包 → 放入环形缓冲
写线程：           从环形缓冲 memcpy → AAudio write
```

**写线程只做搬运，不做运算。** 处理抖动被环形缓冲吸收，不会变成 xrun。

**③ 位置天然包含 DSP 延迟**

读的是 `framesRead`（已播出帧数），已包含 DSP 链的 group delay 与处理延迟。进度条、切换锚定都不需要额外补偿——**不要人为再减「DSP 延迟」，那会减错。**

#### 3.5.4 开关关掉 ≠ 降档（重要）

**错误做法**：用户一开 EQ，就「为了安全」把通路从独占降到系统默认。

| | 独占 + DSP | 系统默认 + DSP |
|---|---|---|
| float 转换次数 | 我方 1 次 | 我方 1 次 + AudioFlinger 1 次 |
| dither | 无 | 有 |
| 延迟 | 低 | 高 |
| 混音 | 无 | 有（可能与其他 app 混） |

**即使不追求位完美，独占 + DSP 依然优于系统默认 + DSP。** 开关关掉只是「允许偏离位完美」，通路仍应选最优档。

```
bitPerfect 只影响：EQ 是否可用 / 采样率是否可选 / 音量是否锁死
bitPerfect 不影响：选哪一档通路
```

两件事解耦，用户就不会遇到「我想调个 EQ，结果音质整个降级了」。

#### 3.5.5 徽章表现

| 状态 | 徽章 |
|---|---|
| 独占 + 开关开 + 无 DSP + 跟随源率 | **已达成** |
| 独占 + 开关关 + 开了 EQ | **已偏离：「已调音」** |
| 独占 + 开关关 + 选了 96k | **已偏离：「已改率」** |
| 独占 + 开关关 + 同时改了 | **已偏离：「已调音 · 已改率」** |
| 系统默认 + 任何 | **不可达** |

注意第 2、3 行：**通路没变，只是徽章从「已达成」变「已偏离」。** 用户能看到「我主动做了这件事，代价是什么」，而不是被静默降级。

## 4. bit-perfect 开关

### 4.1 语义：反锁

**锁的是「用户的选择权」，不是「引擎的适配权」。**

| 开关 | EQ | 采样率选择 | 用户可见效果 |
|---|---|---|---|
| **开** | 强制 bypass，选项灰 | 强制「跟随源」，选项灰 | 引擎自动适配，用户不能干预 |
| **关** | 可开关，选项活 | 可选 44.1 / 48 / 88.2 / 96 / 176.4 / 192 / 跟随源 | 用户自己决定，面板标注代价 |

### 4.2 三个边界

**① 开关不管模式，但「系统默认档」的采样率选项恒灰 —— 理由是档位限制，不是开关限制。**

系统默认档下选 96k = 我方 SRC 到 96k → AudioFlinger 再改回原生率 → 双重 SRC，纯劣化。文案要区分灰的原因：

- 开关开：「位完美已锁定，采样率跟随源」
- 开关关 + 系统默认档：「系统默认档由系统决定采样率」

**② 「系统默认 + 开关开」是合法组合，但不亮徽章。**

这是「我懒得管，你别乱动」的省心档，有存在价值。面板必须直说：

> 锁定已生效，但系统默认档必经系统混音，位完美不可达。选独占档才能点亮。

**③ 开关开着时，用户的「自救能力」被关掉了，所以提示必须给「临时解锁」的快捷入口。**

否则就是把人锁在门外还不给钥匙。

### 4.3 开关变化是否重建流（不对称）

| 变化 | 重建流 | 理由 |
|---|---|---|
| 关 → 开 | **是**（若当前非系统默认档） | 要还原源率 + 关 DSP + 锁音量；若原本已符合则 `Noop` |
| 开 → 关 | **否** | 只是解锁选项，实际参数未变 |

## 5. 设备变化

### 5.1 按方向（无争议，铁律）

| 方向 | 事件 | 行为 |
|---|---|---|
| 输出变**公开** | 拔耳机、断蓝牙、DAC 掉线 | **无条件暂停** + 记位置 |
| 输出变**私密** | 插耳机、连蓝牙 | 可续播 |
| 输出变**更好** | 插 USB DAC | 可续播（+ 提示可切档） |
| 设备消失 | 物理断开 | 必须暂停（通路已不存在） |

一句话：变公开时续播 = 把声音放给一屋子人，任何自动化都不值得冒这个险。

### 5.2 按耗时（决定「续播」还是「暂停」）

**续播或暂停，不该由用户偏好决定，而该由切换耗时决定。**

| 耗时 | 典型 | 行为 |
|---|---|---|
| < 150 ms | 系统默认档重建 AudioTrack | **静默续播**，无提示 |
| 150–800 ms | AAudio 独占重开流 | **续播 + 轻提示**，位置锚定已播出点 |
| > 800 ms | USB DAC 上电枚举、UAC alt-setting | **预建流 → 就绪后暂停** + 明确状态 |

第三档「预建后暂停」是关键：不要切到一半停下来等用户点（那样用户点了还要再等 2 秒），而是后台把流建好、seek 好、只差喂数据，然后停在暂停态。用户按播放 = 立响，零等待。

### 5.3 可行性三类（决定 UI 置灰 / 可选 / 待定）

| 情况 | 例子 | UI |
|---|---|---|
| **结构不可能** | 蓝牙 + 任何独占档；空间音频开启 + 独占 | **置灰**，长按给原因 |
| **设备暂不存在** | USB 独占 + 没插 DAC | **可选**，标「（等待 USB DAC）」 |
| **可行** | 外放 / 3.5mm + AAudio 独占 | 正常可选 |

设备 × 模式：

|  | 系统默认 | AAudio 独占 | USB 独占 |
|---|---|---|---|
| 外放 | ✓ | ✓（多数支持 MMAP） | 等待设备 |
| 3.5mm 有线 | ✓ | ✓ | 等待设备 |
| 蓝牙 A2DP / LE | ✓ | **✗ 结构不可能** | 等待设备（插上也被 USB 抢路由） |
| USB DAC | ✓ | ✓ | ✓ |

**「结构不可能」与「设备暂不存在」必须分开。** 都置灰 → 用户没法提前配好「等我插上 DAC 就用独占」；都放开 → 用户会在蓝牙下反复点一个永远失败的选项。

### 5.4 设备变化 × 模式 矩阵

| 事件 | 系统默认 | AAudio 独占 | USB 独占 |
|---|---|---|---|
| 插 3.5mm | 原生率变则静默重建；续播；无提示 | 关旧流 → 重开（300–600ms）；续播；轻提示 | 无影响 |
| 拔 3.5mm | 重建；**暂停**；无提示 | 重开，外放常不支持独占 → 失败则回退系统默认；**暂停** | 无影响 |
| 连蓝牙 | 重建 + 目标率改 BT 实际率；续播；轻提示（编码不可位完美） | **独占不可行** → `activeRung`→系统默认；续播；轻提示 | 无影响（USB 路由优先级更高） |
| 断蓝牙 | 重建；**暂停**；无提示 | `activeRung` 回独占，重开；续播；轻提示 | 无影响 |
| 插 USB DAC | 重建；续播；轻提示（可切独占） | 重开（独占流路由到 DAC，仍有效）；续播；轻提示（可切 USB 独占） | 若有设备则 open；续播；轻提示 |
| 拔 USB DAC | 重建；**暂停**；阻塞提示 | 回落重开；续播或暂停 | **强制暂停**；阻塞提示；`activeRung` 回系统默认 |

## 6. 状态切换行为链

### 6.1 播放中

```
1. UI 进入「切换中」态
2. 停止喂数据（不 pause 底层流，保持 STARTED）
3. 读已播出位置 P（硬件戳 → framesRead → written−buffer）
4. 锚定基准 base：本次切换链首次则 base = P，否则沿用
5. 关旧流（停线程 → join → 清 handle → close）
6. 开新流（目标率 / 位深 / sharing mode）
7. 回读校验（率、格式、sharingMode）→ 不符走降级链
8. seek 回 base（clamp 到 0 ~ duration−500ms）
9. 恢复喂数据
10. 更新面板 + 徽章（实测）
11. 按耗时给提示（§5.2）
```

**第 3、4 步是全链路最重要的两条：**

- 位置必须取**已播出点**，不能取已写入点。AAudio 独占缓冲 100ms+，按写入位置续播会跳过 100ms 音乐；AB 对比插拔五次 = 跳过 500ms，发烧友立刻听出来。
- 必须**锚定基准**，不能逐次累加。每次续播 ±30ms 误差，插拔五次漂 150ms、十次漂 300ms，用户会发现「同一段越听越不对」。用户主动 seek 或换曲时基准重置。

**失败路径铁律：不允许「回到原模式」。** 原模式此时可能已失效（耳机已拔），统一回退到系统默认，再往上试。做错就退化成「切档死循环」。

### 6.2 未播放时

```
1. 记录暂停位置 P（含 pending seek）
2. 关旧流（若有）
3. 【不立即开流】
4. 更新 preferredMode
5. 面板更新：徽章进入「待定」态
6. 无任何提示
```

**第 3 步：未播放时不预建独占流。**

独占 MMAP 流 open 后，即使不写数据，也占着 HAL 的独占通路，其他 app 的音频会失败或被迫降级。用户暂停着去刷个视频发现没声音 —— 这是最难排查的一类投诉。

| 方案 | 优点 | 代价 |
|---|---|---|
| 预建 + 保温 | 按播放秒开 | **霸占输出，其他 app 静音** |
| 不预建 | 不霸占，行为可预期 | 按播放需 ~0.5s 启动 |
| 预建 + 60s 释放 | 折中 | 逻辑复杂，60s 内仍在霸占 |

**选「不预建」**，把 0.5s 启动成本用「并行 open + 预解码首帧」压到感知最低。发烧友能接受「按下去响得快」，不能接受「暂停时别人放不出声」。

### 6.3 按下播放那一刻

```
并行：解码首帧  ‖  open 新流
     ↓
回读校验（率/格式/sharing）
     ↓
seek 到 P → 开始喂数据
     ↓
徽章 待定 → 已达成（约 1s 内）
```

| 情况 | 行为 |
|---|---|
| open 成功 | 正常出声，徽章点亮，无提示 |
| open 失败 | 降档（一次）→ 出声 + Snackbar 说明（此时用户在等声音，可以出声提示） |
| 全部失败 | 回退系统默认出声 + Snackbar，绝不静默哑火 |
| 目标模式「等待设备」（USB 无 DAC） | 用系统默认出声 + 面板标「USB DAC 未连接」，**不弹框** |

### 6.4 提示分级

**播放中**（有间隙、有位置风险，需要提示）：

| 耗时 | 成功 | 失败 |
|---|---|---|
| < 150 ms | 什么都不显示（连 toast 都不给，避免闪） | — |
| 150–800 ms | Snackbar「正在切换输出…」，成功后立刻消失 | 对话框：原因 + 〔重试〕〔回退系统默认〕〔切其他档〕 |
| > 800 ms | 持续「切换中」状态条 + 完成提示 | 同上，且说明「DAC 枚举可能失败」 |

**未播放**（只是改配置，不打扰）：

| 结果 | 提示 |
|---|---|
| 成功 | **完全静默**，只有面板变化 |
| 失败 / 不可用 | Snackbar 一句，**不用对话框**（没在播，不紧急） |
| 结构不可能 | 置灰，不响应点击 |

**「未播放成功即静默」是这块最该坚持的规则。** 配置类操作不该有仪式感。

同原因同会话只详细解释一次，之后只在面板标记。

## 7. 特殊场景全集

### A. 焦点与系统事件

| 场景 | 音频处理 | 位置 | 提示 | 重建流 |
|---|---|---|---|---|
| 通知音 / 导航播报（瞬态焦点丢失） | 独占档：关闭流让出（见 §8）；共享档：duck 或暂停 | 记已播出点 | 无 | 独占档：是（恢复时重开） |
| 来电（永久槽丢失） | 立即暂停 + 释放流 | 记位置 | 无（系统已有来电 UI） | 是 |
| 闹钟 | 同来电，优先级更高：必须让出 | 记位置 | 无 | 是 |
| 另一 app 请求独占把我们踢掉 | 检测流失效 → 暂停 → 重试一次 → 失败降档 | 记位置 | Snackbar「输出被其他应用占用」 | 是 |
| 耳机线控 / 媒体键 | 走 MediaSession 语义 | 不变 | 无 | 否 |
| 系统处于通话中（`MODE_IN_COMMUNICATION`） | 独占不可用，不许抢通话通路 | 记位置 | 面板标记 | 是（退出通话后重开） |

### B. 音量与静音（结构性冲突）

| 场景 | 音频处理 | 提示 |
|---|---|---|
| 系统媒体音量 → 0 | 独占通路的音量语义由 HAL 决定，**不得假设系统静音会生效**。保守做法：监听后主动暂停 | 面板「系统音量为 0」 |
| 静音 / 勿扰（ringer SILENT） | 同上：主动暂停（降档无效且有害） | 同上 |
| 蓝牙绝对音量开关变化 | 音量语义变化，软件侧不介入 | 无 |
| DAC 硬件音量旋钮 | 我方不可知，不干预 | 无 |

**为什么是「暂停」而不是「降档」**：暂停不破坏位完美，降档破坏。为一个静音键把通路降掉是拿错药。

### C. 设备抖动与重连

| 场景 | 音频处理 | 位置 | 提示 |
|---|---|---|---|
| USB DAC 拔插抖动（<300ms 内多次） | 合并为一次，等稳定后处理 | 保持 | 不提示 |
| USB DAC 供电不足反复重连 | 累计 3 次失败 → 停止重试 | 保持 | 阻塞提示「USB 供电不足或不稳定」 |
| 蓝牙被另一设备抢占（多点连接） | 立即暂停 | 记位置 | 无（用户知道自己在干什么） |
| 蓝牙 A2DP ↔ LE Audio profile 切换 | 视为设备变化，重新探测率 | 记位置 | 面板更新 |
| 蓝牙编解码器变更（SBC → LDAC，率变） | 目标率重算 + 重建 | 记位置 | 无 |
| USB-C 耳机（headset 类） | 按 USB DAC 处理 | — | — |
| HDMI / 投屏插拔 | 路由变化，重新探测 | 保持 | 面板更新 |
| 投屏 / Cast 接管输出 | 本地暂停 + 释放本地流 | 记位置 | 「已切换到投屏输出」 |

### D. 系统策略介入

| 场景 | 音频处理 | 提示 |
|---|---|---|
| 空间音频（Spatializer）开启 | 系统在输出链插入虚拟化 → 独占失效，位完美不可达 | 轻提示 + 徽章「不可达：空间音频已开启」 |
| 系统「媒体输出」偏好设备变更（Android 13 媒体路由） | 视为设备变化 | 面板更新 |
| 免打扰 / 驾驶模式 | 除静音处理（见 B）外无特殊逻辑 | 无 |
| 电池优化冻结后台 | 前台服务 + `PARTIAL_WAKE_LOCK` | 无 |

### E. 资源与调度

| 场景 | 音频处理 | 要点 |
|---|---|---|
| 息屏 / Doze | 保持 `PARTIAL_WAKE_LOCK`；**缓冲临时加大**（如 100 → 200ms）降低 underrun | 独占流最怕调度延迟 |
| 省电模式 | 同上，**但不降档**（降档解决不了调度问题） | — |
| **网络欠载** | **绝不判为设备故障**：解码器没数据 ≠ 写线程失败 | 历史事故点，必须区别对待，不降档 |
| 解码阻塞（大文件 seek） | 写线程喂空 → 输出静音，不判故障 | — |
| 相机 / 重负载并行 | 加大缓冲 | — |

### F. 内部控制变化

| 场景 | 重建流 | 说明 |
|---|---|---|
| bit-perfect 开关：关 → 开 | **是**（当前非系统默认档时） | 还原源率 + 关 DSP + 锁音量；原本已符合则 `Noop` |
| bit-perfect 开关：开 → 关 | **否** | 只解锁选项，参数未变 |
| 自选采样率变化 | 是 | 目标率变了 |
| EQ 开 / 关 | **否** | **换处理链 ≠ 换流**；徽章随之在「已达成 / 已偏离」间切换 |
| 位深不匹配（切歌时） | 是（切歌边界） | 不在曲中重开 |

「换处理链 ≠ 换流」这条要记住：DSP 在 float 域做完再一次性转目标位深，流本身不用动，只是位完美徽章熄灭。

### G. 并发与竞争

| 场景 | 处理 |
|---|---|
| 快速连续点切模式 | debounce 400ms；只执行最后一次；切换进行中时最多排一个待处理 |
| seek 与切换叠加 | 串行化：切换优先，seek 在切换完成后基于新基准应用 |
| 切歌与切换叠加 | 串行化：切换完成后重新取当前曲目参数 |
| 播放 / 暂停与切换叠加 | 暂停请求在切换完成后应用，不打断切换 |
| 设备抖动与用户操作叠加 | 用户操作优先；位置以最后一次已播出点为准 |

统一实现：**所有流操作进一个串行队列，队列里最多保留一个「最新意图」，中间的合并掉。** 不做这件事，就会出现「用户狂点三下，流被打开三次」这类竞争。

## 8. 独占流的结构性代价

这条必须写进设置项的说明里，不能藏。

独占 = 独占物理输出。持有期间：

- 通知音、闹钟、导航播报无法从同一设备出声（或被迫走别的设备）
- 系统静音 / 媒体音量可能不生效（由 HAL 决定，不可假设）
- 其他 app 的播放失败或被迫降级

### 8.1 让出策略两选一

| 策略 | 行为 | 代价 |
|---|---|---|
| **兼容优先（默认）** | 检测到瞬态焦点丢失 → 关闭独占流让出 → 恢复后重开 + seek 回基准 | 恢复时 300–600ms 间隙 |
| **纯净优先（发烧友可选）** | 不主动让出，通知 / 闹钟静音 | 用户明确承担 |

**为什么是「关闭」而不是「暂停」**：本机实测 `requestPause` 后流停在 PAUSING 且恢复不可靠；关闭是唯一确定的状态，也是唯一能让 HAL 释放通路的方式。

## 9. 区分「设备故障」与「上游欠载」

历史事故总结：**降级只能由确定性证据触发，不能由启发式猜测触发。**

| 证据 | 属于 | 允许降档 |
|---|---|---|
| 打开回读不符（sharingMode / 率 / 格式） | 设备能力 | 是 |
| 连续写超时 + `framesRead` 不增长满阈值（≥3s，且队列非空） | 设备故障 | 是 |
| 路由变化 | 设备变化 | 是（重算，不降档） |
| **队列为空 / 解码器没数据** | 上游欠载 | **否** |
| `getState` 返回值 | **不可信**（HAL 会谎报 PAUSING 而实际正常播放） | **否** |
| 单次写超时 | 抖动 | 否 |
| 位置跳变 | 时钟抖动 | 否 |
| UI 卡顿 | 无关 | 否 |

## 11. 反面清单

1. 不许用设备型号 / 品牌白名单决定通路。
2. 不许用 `getState` 当健康信号。
3. 不许在曲中无限重开同一档（黑名单必须有）。
4. 不许在 **bit-perfect 已达成状态（徽章亮）** 下做 float 中转、归一化、DSP。
5. 不许把「能播出声」等同于「位完美」。
6. 不许让用户直接选通路实现（只选意图）。
7. 不许设备变化时改动 `preferredMode`。
8. 不许未播放时预建独占流霸占输出。
9. 不许把上游欠载误判为设备故障而降档。
10. 不许「切档失败后回到原模式」（统一回退系统默认）。
11. 不许用淡出实现切换（淡出破坏位完美；直接停）。
12. 不许把「续播位置」做成逐次累加（必须锚定基准）。
13. 不许把**控制面**（切换编排、降级决策、失败提示）下沉到 native。
14. 不许以「更底层更稳」为由搬迁代码，除非有 §13.6 的可量化指标。
15. 不许为了「将来可能下沉」而扭曲现在的接口设计（打平成 C 结构体、加 JNI 签名约束）。
16. **不许先 SRC 再 open**——必须先 open、回读真实率，再定 SRC 目标（否则变调）。
17. **不许改采样率后沿用旧 EQ 系数**——biquad 系数是采样率的函数。
18. **不许「开 DSP 就自动降档」**——bitPerfect 只影响选项可用性，不影响通路选择。
19. 不许把 DSP 运算放在写临界路径里（写线程只搬运）。

## 12. 分期与验收

| 期 | 内容 | 验收 |
|---|---|---|
| **1** | 概念重构：三档模式 + 反锁开关 + 双层模式 + `reconcile` 纯函数 + 目标率统一 | 3 档 × 2 开关 × 5 路由 × 4 源参数的组合单测全绿；UI 灰态与文案正确 |
| **2** | 系统默认档主动 SRC（含「同率不 SRC」） | 44.1k 源在 44.1k 设备上 SRC 函数未被调用（调用计数可断言） |
| **3** | 播放 / 未播放两套切换行为链 + 提示分级 + 位置锚定 | 真机：三档互切各 10 次，位置漂移 < 50ms；无静默降级 |
| **4** | 特殊场景 A–G 全覆盖（重点：焦点让出、静音冲突、网络欠载区分、抖动合并） | 通知 / 来电 / 拔插抖动 / 息屏长播 各 10 次无异常 |
| **5a** | USB 直通档（AAudio + USB 路由，`getSampleRates()` 选率） | 插 DAC 自动切换、徽章点亮 |
| **5b** | 真 UAC 独占（可选，暂缓） | — |
| **6** | Oboe 接入（A/B，保留 AAudio） | 同一契约测试两实现全绿，真机无回归 |

### 契约测试（所有 sink 实现必须通过）

1. 实现 `setOutputStreamOffsetUs` 并加进 `getCurrentPositionUs`。
2. 首次写成功后立即返回有效位置，不得长时间返回 `CURRENT_POSITION_NOT_SET`。
3. 对外位置单调不减（seek 除外），由 sink 自己保证，不依赖 renderer 的 `max()` 兜底。
4. 位置来源优先级：硬件时间戳 → `framesRead − base` → `written − buffer`。
5. 永不 `pause` / `flush` 底层流来表达暂停；保持 STARTED，靠停喂。
6. 关闭顺序：停写线程 → join → 清 handle → close。写线程自己不许 close。handle 必须 volatile。
7. EOS 后位置推到尾部，并正确上报无待播数据。
8. **DSP 开启时**，位置仍单调、仍等于已播出点，且不因处理链长度（EQ 开关、SRC 目标变化）而跳变。

## 13. 附录 A：native 与 Kotlin 的边界

**问题**：播放中切换涉及的音频操作，值不值得下沉到 native？还是先在 Kotlin 做，等没故障了再下沉？

**结论先行**：不为了「更底层」而下沉，只为可量化的指标而下沉。「等没故障」不是判据，**「故障发生在哪一层」才是判据**。当前形态（控制面 Kotlin + 数据面 native + 每 100 ms 一次 JNI）已经接近最优。

### 13.1 收益量化：JNI 频率

| 项 | 数值 |
|---|---|
| 播放稳态 `write` 频率 | 44100 Hz / 4410 帧（100 ms）≈ **10 次/秒** |
| 一次模式切换的控制面 JNI 调用 | `close` + `open` + 3 次参数回读 + `seek` ≈ **6 次** |
| JNI 单次开销（简单参数） | 1–5 µs → 6 次 ≈ **30 µs** |
| 占切换总耗时（200–600 ms）比例 | **≈ 0.01%** |

下沉省下的时间连一帧 UI 预算（16 ms）的零头都不到。**收益为零。**

只有当缓冲降到 64 帧级（约 690 次/秒）才值得讨论接口频率——而那时该做的是**合并接口**，不是搬家。

### 13.2 三条成本

| # | 成本 | 具体 |
|---|---|---|
| 1 | **崩溃可读性归零** | 历史全部事故（use-after-free、无限重播、watchdog 误杀、`setOutputStreamOffsetUs` 静默丢失、位置为负）**全部在控制面**。留在 Kotlin 可直接读栈、断点、加日志；下沉后要 tombstone + `addr2line`，且 Kotlin↔native 边界本身是新的故障源（JNI 全局引用泄漏、线程 attach/detach、跨边界异常） |
| 2 | **可测性归零** | `reconcile` 120 组合在 JVM 上几百毫秒跑完；下沉后要 gtest + 交叉编译 + 真机。且改代码的门槛从「会 Kotlin」变成「会 C++ 且懂音频」，直接损害开源目标 |
| 3 | **状态倒挂** | 切换要与 UI 状态、MediaSession、焦点、路由回调、持久化同步，这些全在 Kotlin。下沉后 native 必须逐项 JNI 回调上来，形成「native 管着 Kotlin 的状态」 |

### 13.3 越界下沉的反面形态

```cpp
// 假设把「切换」下沉后的形态
int switch_rung(JNIEnv* env, jobject thiz, int targetRung) {
    stop_feeding();                       // ← 要与 Kotlin 的 playing 状态同步
    long pos = read_position();
    close_stream();

    if (open_stream(cfg) != OK) {
        env->CallVoidMethod(ui, notifyMethod, r);   // ← 通知 UI 弹框，倒挂第一处
    }

    long dur = get_duration_us();         // ← duration 在 Kotlin 解码器里，又得回调
    seek(clamp(pos, 0, dur - 500000));    // ← 又一处跨边界

    start_feeding();
    return OK;
}
```

**每一行都要一次跨边界同步或回调。** 结果比全在 Kotlin 更慢、更乱、更脆——把 11 步线性流程变成 11 次跨语言穿越。

### 13.4 「等没故障了再下沉」为何是错判据

| # | 问题 |
|---|---|
| 1 | **「没故障」不会到来**。稳定性是持续维护的属性，不是一次性状态。真到了那一天，你也不会再有动力去动它——结论对，理由错 |
| 2 | **下沉本身制造新故障**。把已验证的控制面搬到新语言新边界，等于把「已验证」重置为「未验证」，且新故障排查成本更高。净损失，不是投资 |
| 3 | **污染当下设计**。为「将来可能下沉」而把状态打平成 C 结构体、给纯函数套 JNI 签名约束——为一个不会发生的迁移牺牲当下的可测性 |

### 13.5 边界固化四件事

边界画对，下沉从「必经之路」变成「随时可选项」；画错，下沉就是二次返工。

| 动作 | 收益 |
|---|---|
| **sink 契约固定**（§12 七条 + 测试） | AAudio / Oboe / AudioTrack / USB 四实现可互换，在哪一层都无所谓 |
| **控制面写成纯函数** `reconcile(Desired, Actual) → Action` | 无副作用、无 Android 依赖 → 换层只是换语言，不换结构 |
| **数据面接口粗粒度**：`open(cfg)` / `write(buf)` / `getClock()` / `close()` | JNI 频率与缓冲次数同阶（10 次/秒），不是每帧 |
| **必须原子的一小块单独做 native 原语** | 如「读位置并保证流存活」，只做这一处，不做整个编排 |

### 13.6 三个可量化触发条件

只有这三条成立时才考虑下沉，而不是「跑得稳不稳」：

| 触发条件 | 怎么知道 | 该怎么改 |
|---|---|---|
| JNI 频率成为瓶颈 | 每秒 > 数千次 | **先合并接口粒度**，不是搬家 |
| GC / 调度导致 underrun | `AAudioStream_getXRunCount()` 持续增长，且缓冲加到 200 ms 仍不改善 | 改 Oboe **callback 模式**（HAL 线程直接拉），不是下沉编排 |
| 多个 native 模块需复用同一音频内核 | 出现第二个调用方 | 抽出 kernel，仍不碰编排 |

第二条尤其要注意：**GC 风险的解法是缓冲策略与回调模式，不是语言选择。** C++ 不提供实时保证，只有「不在回调里分配内存」这类纪律才提供。

### 13.7 关于 Oboe callback 模式

若将来换 Oboe callback 模式，写循环会自然变成「native 回调里从环形缓冲取数据」。那时的边界是**自然生成**的：

- 环形缓冲读写指针 → native
- 「有没有数据 / 该不该暂停」 → 仍由 Kotlin 决定

**好的边界是自己长出来的，不是提前规划出来的。**
